# یادداشت امنیت و مسیر آماده‌سازی وردپرس

این شاخه فقط لایه رابط کاربری HTML را تکمیل می‌کند. ظاهر فرم یا داشبورد به‌معنای وجود سرویس امن نیست.

## مواردی که باید پیش از انتشار عملیاتی پیاده‌سازی شوند

1. **احراز هویت فقط با موبایل و OTP:** ایمیل و رمز عبور در مدل حساب کاربری وجود نداشته باشد. شماره موبایل نرمال‌شده و یکتا شناسه ورود باشد. کد یک‌بارمصرف با مولد رمزنگارانه تولید، فقط به‌صورت hash ذخیره، با TTL کوتاه (مثلاً ۲ تا ۵ دقیقه)، مصرف یک‌باره و محدودیت ارسال/تلاش/IP/شماره اعتبارسنجی شود. پاسخ API نباید وجود یا عدم وجود شماره را افشا کند. پس از تأیید، نشست امن وردپرس با کوکی‌های Secure/HttpOnly/SameSite صادر شود. نقش کاربر هرگز از فرم، query string یا localStorage پذیرفته نشود و فقط از capabilityهای سمت سرور به دست آید.
2. **چرخه ثبت‌نام:** دریافت نام، نام خانوادگی، شماره موبایل و نوع ثبت‌نام؛ تأیید مالکیت شماره با OTP قبل از ایجاد حساب/ثبت‌نام. شماره نرمال‌شده باید unique index داشته باشد. تغییر شماره نیز فقط با OTP شماره جدید انجام شود. هیچ وابستگی اجباری به ایمیل وجود نداشته باشد.
3. **مجوزدهی:** تعریف نقش‌ها و capabilityهای حداقلی مانند مدیر همایش، دبیر، نویسنده، داور و شرکت‌کننده. کنترل دسترسی در هر درخواست سمت سرور انجام شود؛ مخفی‌کردن لینک کافی نیست.
4. **CSRF و فرم‌ها:** استفاده از nonce وردپرس و بررسی آن در handlerهای سمت سرور، همراه با اعتبارسنجی نوع/محدوده ورودی، sanitize و escape خروجی متناسب با context.
5. **ارسال مقاله:** محدودیت حجم و پسوند، بررسی MIME واقعی و امضای فایل، نام‌گذاری تصادفی، عدم اعتماد به نام فایل، ذخیره خارج از مسیر عمومی یا محافظت‌شده، کنترل دسترسی دانلود و اسکن فایل. اعتبارسنجی JavaScript فقط برای تجربه کاربری است.
6. **XSS و SQL injection:** استفاده از APIهای امن وردپرس، `$wpdb->prepare` برای SQL، و توابع escaping مانند `esc_html`, `esc_attr`, `esc_url`, `wp_kses_post` هنگام نمایش.
7. **پیامک و سرویس‌های بیرونی:** کلید API فقط در سمت سرور/مدیریت اسرار، محدودیت نرخ، ثبت نتیجه ارسال، رضایت گیرنده و امکان لغو دریافت. هرگز کلید را داخل HTML یا JS قرار ندهید.
8. **حریم خصوصی:** حداقل‌سازی داده، تعیین زمان نگهداری، سیاست حذف/خروجی داده، دسترسی محدود به فایل‌های مقاله و سوابق داوری.
9. **ثبت رویداد و پشتیبان‌گیری:** ثبت تغییرات حساس (وضعیت مقاله، تخصیص داور، پرداخت، صدور گواهی)، پشتیبان‌گیری رمزگذاری‌شده و آزمون بازیابی.
10. **پرداخت:** تأیید پرداخت فقط با اعتبارسنجی callback سمت سرور و استعلام از درگاه؛ هرگز به پیام موفقیت مرورگر اعتماد نکنید.
11. **آزمون انتشار:** آزمون واحد/یکپارچه، تست دسترسی نقش‌ها، تست فایل‌های مخرب/بزرگ، بررسی امنیتی افزونه‌ها، HTTPS و تنظیمات سرور.

## مدل داده پیشنهادی

- Conference و ConferenceEdition
- UserProfile و Membership/Role
- Paper و PaperAuthor و PaperFile
- ReviewerProfile و ReviewAssignment و Review
- Registration و Payment و Invoice
- Message و Notification و SmsLog
- Certificate و CommitteeMember و Post

همه رکوردهای وابسته باید به شناسه دوره همایش متصل باشند تا سامانه چندهمایشی و چنددوره‌ای قابل اتکا باشد.

## معیار پذیرش رابط HTML

- نمایش مناسب در موبایل، تبلت و دسکتاپ و پشتیبانی از RTL.
- کنترل‌های تعاملی دارای label و focus قابل مشاهده باشند.
- جدول‌های عریض در صفحه کوچک اسکرول افقی داشته باشند.
- هیچ پیام یا دکمه‌ای ادعا نکند داده ذخیره/ارسال شده، مگر اینکه backend واقعی آن را تأیید کرده باشد.

## سیاست اعلان‌های سامانه: پیامک‌محور

تمام رویدادهای قابل اطلاع‌رسانی باید از یک Notification Service سمت سرور عبور کنند و پیامک کانال اصلی/پیش‌فرض باشد: تأیید شماره، ثبت‌نام و پرداخت، دریافت مقاله، تغییر وضعیت مقاله، تخصیص و یادآوری داوری، نتیجه داوری، اصلاحات درخواستی، پذیرش/رد، برنامه همایش و صدور گواهی. برای هر پیام، قالب نسخه‌بندی‌شده، شناسه رویداد، گیرنده، وضعیت صف/ارسال/تحویل/خطا، زمان، شناسه اپراتور و شمارنده retry ثبت شود. ارسال پیامک نباید داخل درخواست وب هم‌زمان انجام شود؛ از صف و worker استفاده شود. برای جلوگیری از افشای اطلاعات، متن پیامک حاوی جزئیات حساس مقاله یا داوری نباشد و کاربر را به پنل امن هدایت کند. OTP و پیامک‌های تراکنشی از پیامک تبلیغاتی جدا باشند. سیاست رضایت، لغو پیامک‌های غیرضروری و محدودیت هزینه نیز پیاده شود.

**نکته پیاده‌سازی:** صفحات HTML فعلی صرفاً نمایشی‌اند؛ هیچ پیامک یا OTP واقعی ارسال/تأیید نمی‌شود. endpointها باید در WordPress REST API یا handler امن پیاده‌سازی شوند و کلید سرویس پیامکی فقط در سرور نگهداری شود.
